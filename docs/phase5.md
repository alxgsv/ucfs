# Phase 5 acceptance: hardening

Measured on 2026-11-08 on three hosts:

- **macOS:** the Apple Silicon Mac of the earlier phases, macOS 27.0.1, NFS front-end, nothing installed.
- **Linux VM:** an OrbStack machine on that Mac, Ubuntu 26.04.1 arm64, kernel 7.2.9, Go 1.26.8 and `fuse3` from the
  Ubuntu archive, created for this phase. It has root, so it ran the FUSE tests under `-race` (cgo) and mounted the
  Linux NFS front-end, the two gaps the earlier Linux host (no cgo, no sudo) left open; it also had a second user for
  the access checks. FUSE was mounted both as root (`mount(2)`) and as a normal user through `fusermount3`.
- **CI:** `.github/workflows/ci.yml` (see *Benchmarks and CI*).

Most of the acceptance runs against `internal/fake`, through the real `ucfs` command: the tests in `cmd/ucfs` run it
in-process with `apiTransport` pointing its REST and Upload API requests at the fake and `--cdn-base` at the fake CDN,
and mount for real (NFS on macOS, FUSE or NFS on Linux) when `UCFS_MOUNT_TESTS=1`. The fake gained what hardening needs:
a REST denial with the live API's 403 body, persistent throttling, CDN failures by status, an original whose content
changes under its uuid, content generated by chunk so ranges of large files cost only their bytes, and default CDN and
REST latencies.

The live runs used `alex-gusev-test` (Uploadcare name `alex_gusev_test`), whose 18 files are the user's: 6 PNGs and 12
copies of a 244 MB WebM. Their uuids, names, sizes, upload times, metadata and tags were recorded before the first
request of the phase and compared at the end (*End state*). Every live mount used `--views tree` (the fixtures appear
only by name in `tree/_inbox/`), nothing read a fixture, and Finder was opened only on `tree/` directories of the
phase's own uploads. Test files were photo-like JPEGs from `spikes/photogen`, uploaded with metadata `ucfs:test=1`:
a probe of 22,191 B, 20 of 21.6–22.4 KB, one of 3,519,550 B, one of 12,208,903 B, and the soak's small JPEGs.

## Traffic budget

`--traffic-budget 500MB` (or `2GiB`, `500MB/day`) caps the CDN bytes a project reads per calendar day in the local zone.

- **What counts.** The bodies of range reads, which is what the CDN serves for file content. A `HEAD` carries no body
  and does not count, so `stat` of a variant and `user.uc.md5` keep working past the budget; neither do REST requests,
  which are no CDN traffic, nor the CDN's 400 pages (about 1 KiB each, still read for the error message). Cached
  blocks are served past the budget.
- **Never past the limit.** A block is counted before it is fetched and given back if the fetch fails, so concurrent
  fetches never take the count over the limit: the 2 MiB runs fetched exactly 2,097,152 B.
- **Prefetch stops first.** Prefetch only takes a block while more than a reserve, a tenth of the budget and at most
  16 MiB (one full prefetch window), would remain; the reserve goes to reads someone waits for.
  `TestBudgetStopsPrefetchFirst`: with 20 blocks of budget, prefetch took at most 18 and demand reads the last 2.
- **Persisted.** The count is kept in the index (`sync_state`), flushed every 5 s and at unmount, so a remount does not
  start the day over, and mounts of one project share it: each adds what it counted.
- **Errors.** A read that needs bytes past the budget fails with `EDQUOT`: "Disc quota exceeded" on macOS through
  `NFS3ERR_DQUOT`, "Disk quota exceeded" on Linux. `ucfs status` shows used, remaining, the reset time, reads refused,
  and whether prefetch stopped; the log says once per window that the budget is reached.
- **FUSE on Linux 7.x.** The kernel's buffered read path (iomap) reports any failed FUSE read as EIO, which is what the
  first Linux run showed. A file larger than what the budget has left is therefore opened with direct I/O, where the
  reader gets the daemon's errno; every other file keeps the page cache. Such a file cannot be `mmap`ed while the
  budget is that low.

**Finder with the budget** (against the fake, since `by-date/` of the live project holds the user's videos): a
`by-date/2026/11/08/` window with 14 photos read all 14 in full on opening, 14 GETs and 837,643 B, the sum of their
sizes (as Phase 1 found for `files/`). With 210,933 B left of a 1 MiB budget, the next day's window got 3 more photos
(177,568 B) and then 10 reads refused, one per remaining photo, without retries in the 25 s watched. In the live soak, Finder on `tree/p5soak` read the soak's uploads, which the upload had put in
the block cache, so its thumbnails cost no CDN bytes (*Soak*).

## Errors and the degraded API

**One errno table.** `internal/api/errno.go` maps every failure of the REST API, the Upload API and the CDN, and the CDN
client returns typed errors (`ErrNotFound`, `BadRequestError`, `StatusError`) for it to map. `TestErrnoTable` sends the
real requests to the fake and checks each mode:

| Failure | errno |
|---|---|
| REST 404, CDN 404 | `ENOENT` |
| REST 403 `permission_error`, 401, CDN 403 | `EACCES` |
| REST 429 past the Retry-After retries (5, or a Retry-After over 60 s), Upload API 429, CDN 429 | `EAGAIN` (NFS3ERR_JUKEBOX over NFS) |
| REST 5xx, Upload API 5xx after its retries, CDN 503, a refused connection, a range with another ETag | `EIO` |
| CDN 400 (a variant it cannot render) | `EINVAL` |
| a read-only view, an unsupported call | `EROFS`, `EOPNOTSUPP` (errnos the filesystem returns pass through) |
| the traffic budget | `EDQUOT` |
| the degraded API (below) | `EACCES` denied, `EAGAIN` throttled |

A network error used to reach callers as `ECONNREFUSED` from inside the `url.Error`; it is `EIO` now.

**REST bound.** At most 4 REST requests are in flight (`api.MaxREST`), counted per HTTP attempt so a throttled request
frees its slot while uploadcare-go waits out Retry-After. `TestRESTBound`: 12 concurrent info requests at 50 ms each
peaked at 4 in flight and took three rounds, so a `getfattr -R` that refreshes many files cannot flood the API. The
Upload API keeps its own bounds (8 uploads, 4 parts each).

**Degraded mode.** The client records how REST answered lately: ok, denied (401 or 403, with what the API said) or
throttled (429), and since when. Once denied or throttled has lasted a sync interval:

- the mount keeps serving the index and the block cache, and the CDN, which still served the project of Phase 3 after
  its REST access was revoked;
- writes that would need the API fail before anything is spooled: creating a file in `tree/` or `files/`, an overwrite,
  `rm`, `mv` and metadata or tag changes of uploaded files, with `EACCES` when denied and `EAGAIN` when throttled;
  local-only files (`.DS_Store`, `._*`) and empty directories still work;
- `getxattr` and `ucfs resolve` serve the index's copy instead of refreshing (a refresh would wait out the retries);
- `ucfs status` says `API denied since <time>: <detail>` or `throttled since <time>`, with `(serving the index; writes
  refused)`, and the index line `N syncs failed in a row, the last with: <error>; next try in <d>`.

The sync loop backs off: the wait doubles from the sync interval with every failure in a row, up to 10 minutes, and
only the first failure of a streak is logged as a warning (the rest at debug, the recovery at info). `TestLoopBacksOff`:
about 5 syncs in 330 ms against a refusing fake at a 10 ms interval, where 33 would have run. A mount whose index has
been synced once starts without waiting for the API and syncs in the background; only an index never synced needs the
first listing to go through. ("Synced once" is the recorded full scan, not the cursor: an empty project never gets a
cursor, and the first version of this check refused to mount one while throttled.)

**Throttled writes over NFS.** macOS retries a JUKEBOX answer: a `create` in `tree/` with the fake throttled was sent
again after 1, 4, 8 and 16 s and failed with "Operation timed out" (`ETIMEDOUT`, the `soft` mount) after 28.1 s
(`TestMountThrottledWrite`, opt-in). If the throttling ends within that window, the write goes through. On FUSE the
writer gets `EAGAIN` at once.

## Read integrity

The CDN answered the same ETag on `HEAD` and on every `206` of the same object, strong on an original
(`"20e55459064c43df518a6f9579de06d6"`, the probe's MD5) and weak on a variant (`W/"de14240e…"`), and on a `416` too
(live probe, two ranges each). So every range's ETag is compared with its object's: a variant's is the one its `HEAD`
gave (its blocks are stored under it), an original's the one its first range in this process returned. The comparison
is weak (RFC 9110), ignoring `W/`.

On a mismatch the object's blocks are dropped and the read fails with `EIO`: a reader that already received earlier
blocks of the old content would otherwise end up with a file made of both, and retrying the one read cannot undo the
reads before it. The next access to a variant sends a new `HEAD` and reads the new rendering whole. Because NFS has no
open handle, the cache tracks it per object: every content change bumps the object's epoch, a read that continues a
sequential stream begun in an earlier epoch fails once (a read from offset 0 starts over), and a read during which any
fetch saw a change fails too. That last rule came from a test: a prefetch saw the change first and adopted the new
ETag, and the reader's next block came back new without an error. Blocks of an original fetched before a change are
refused when stored after it. The same epoch also covers a variant whose daily `HEAD` finds a new ETag: a reader in
the middle of it gets `EIO` instead of mixed blocks, which §4.4 left open.

## Backpressure

`--max-inflight` (default 32) bounds the CDN requests a mount has in flight (`cdn.Limiter`):

- reads someone waits for, and `HEAD`s, go before prefetches;
- prefetches hold at most three quarters of the slots, so a read finds a slot free however much is being prefetched;
- in each class, the objects waiting take turns, so one reader with many queued requests cannot hold back another;
- a prefetch takes its budget and joins or starts a fetch only once its slot is free, so a reader that catches up with
  a queued block fetches it at its own priority; queued prefetches cost no goroutine, and past 1,024 waiting, new ones
  are dropped;
- `FetchTimeout` (2 min) starts when the request has its slot, not while it waits.

`ucfs status` shows requests in flight and waiting, reads that waited and for how long, and prefetches dropped.

| Cold 64 KiB reads, 30 per run (fake, 30 ms CDN latency, 8 slots) | p95 |
|---|---:|
| alone | 37 ms |
| beside 4 readers streaming 64 MiB files, with the limiter | 34 ms |
| beside them, with a plain semaphore of 8 | 304 ms |

(Under `-race`: 44, 42 and 642 ms.) Live on macOS, 10 cold reads of the 22 KB images each: p50 265 ms and p95 420 ms
alone, p50 371 ms and p95 727 ms beside a reader streaming the 12 MB image with the page cache off (`F_NOCACHE`, 21.6 MB
in two passes, `--cache-size 4MiB` so each pass reached the CDN). No read waited for a slot (`waits` 0): the slowdown is
the downlink shared with 24 concurrent 1 MiB prefetches, which a queue cannot divide; a bulk reader on a slow link would
need fewer prefetch slots (`--max-inflight`).

## Security

- **Config file.** A config file group or others can read is refused with the fix in the message (above);
  `--insecure-config` uses it anyway. The user's own file is 0600.
- **Private directories.** The cache dir and its `blocks/`, `spool/` and `shadow/` are made 0700 at mount if they are not
  (the log says so), the index and its `-wal` and `-shm` files 0600, the journal and lock file 0600 as before. The
  control socket is 0600 inside the cache dir; a socket that does not fit there goes to a per-user 0700 directory in the
  temp dir, refused if it is a symlink or another user's (the shared `/tmp` on Linux).
- **Mount options.** `nosuid,nodev` on every mount: added to the macOS and Linux NFS option strings and to the FUSE
  options, which `fusermount3` adds anyway and go-fuse turns into mount flags for a direct `mount(2)`. `findmnt` in the
  VM: `nfs rw,nosuid,nodev,…,sec=sys` and `fuse.ucfs rw,nosuid,nodev,noatime,user_id=0,…`. No `allow_other`.
- **Other users and the NFS mount.** go-nfs granted every bit ACCESS asked for, and offered only `AUTH_NULL` at MOUNT,
  so macOS sent no uid at all: any user who could reach the mount point could read the project through it (home
  directories on macOS are 0750 with group `staff`, which every local user is in). MOUNT now offers `AUTH_UNIX` only,
  and ACCESS grants nothing to uids other than the daemon's and root (`AccessFilter`, a patch in `third_party/go-nfs`).
  In the VM, a second user got "Permission denied" for `ls`, `cat` and `stat` on both a root-owned NFS mount and a
  root-owned FUSE mount, where root read the same files.
- **Secrets in logs.** Log attributes and error messages replace both key values with `<public key>` and `<secret key>`;
  the public key is part of the default cache path, so an error naming a socket or the index carried it
  (`…/Library/Caches/ucfs/<public key>/ctl-3e5b015b.sock` now). `spikes/keygrep` counts the keys in files without
  printing them:

  | Log (`-v`, live) | bytes | public key | secret key |
  |---|---:|---:|---:|
  | macOS mount, 22 uploads | 19,892 | 0 | 0 |
  | macOS mount, budget | 1,201 | 0 | 0 |
  | macOS mount, fairness | 6,860 | 0 | 0 |
  | Linux FUSE mount, budget | 8,035 | 0 | 0 |
  | macOS mount, cleanup | 3,264 | 0 | 0 |
  | macOS live soak, 2 hours | 19,891 | 0 | 0 |

  The fake soak's 1.7 MB log has 0 hits for the fake keys it ran with.

**What a local attacker could reach.** Measured in the VM:

- Through the mount point: nothing as another user (above). The user's own processes can read and write everything
  the mount shows, as with any mount.
- Through the NFS port: everything. The server listens on `127.0.0.1` on a random port with no authentication, and
  AUTH_UNIX proves nothing: a second user speaking NFSv3 to the port with `go-nfs-client` read `files/` and a file in
  it, claiming its own uid and claiming root alike (go-nfs checks no credentials on READ or READDIR; ACCESS only
  advises the kernel client). With the same RPCs it could create, overwrite and remove what the mount may (uploads,
  soft-deletes of files the mount wrote, foreign files with `--allow-foreign`), with the daemon's credentials. A check
  of the client's source port would not help on macOS, where unprivileged processes may bind ports below 1024. The fixes
  are a front-end without a network port (FUSE-T in V1.1) or a check of the peer socket's owner, which needs the
  socket table (`sysctl net.inet.tcp.pcblist_n`) on macOS.
- The control socket (0600) and the cache dir (0700) are the user's only; the config file is refused unless 0600.
- Root can read everything, as always.

## Node ids

Node ids were plain 64-bit FNV-1a hashes with no collision check (§4.3). A collision would have been concrete on FUSE,
where go-fuse keys inodes by number and would have served one node for the other, and for nodes known by path on NFS,
where `node_ops` keeps the first path recorded for an id (`INSERT OR IGNORE`), so a handle could resolve to the other
path. Now the front-ends take ids from `FS.ID`, which records the key each id was first handed out for, by a second
hash (FNV-1, so a key colliding in both is out of reach), and for nodes known by path also checks the path recorded in
`node_ops` by an earlier run. A key whose id is taken gets a salted hash, and the salt goes to a new index table,
`node_salts`, so the key keeps that id across restarts and its NFS handles resolve. Inode numbers of objects (tree
files, shadow files) cannot move, so a hashed id that meets one is the one salted. Ids remembered for the check are
bounded at 2^18 (then forgotten, salts kept); a collision with a node handed out before that has a chance near 2·10⁻⁹.
`TestIDCollisionIsSalted` and `TestIDCollisionWithRecordedPath` force collisions through an injected hash. The check
costs 0.94 ms per 10,000 ids, under 1% of the 126 ms `ls -l` of 10,000 entries.

## Small items closed

- **`ucfs index refresh <uuid>...`** reads files' current info, metadata and tags included, into the index; a file the
  API no longer knows is marked removed. A running mount sees it at once (the index is shared).
- **Groups the API no longer lists are pruned.** Group sync lists every group with each sweep and drops the ones not
  listed, one request per thousand groups, so a deleted group leaves `groups/` within a sweep.
- **Names with a backslash upload.** A base upload keeps only what follows the last backslash (Spike D), so such a name
  goes up with underscores and whole in metadata `ucfs:name`, which the index shows in every view; an overwrite under a
  plain name drops it. Before, such names were `EINVAL`.
- **Directory renames are not atomic** (documented in PLAN item 23): one metadata `PUT` per file below; if one fails, the
  files moved so far are under the new path and the rest under the old, and the error reaches `mv`. `mv old/* new/`
  completes it. While the API is degraded, the first `PUT` is refused before anything moves.

## Soak

`make soak` (`SOAK=24h` by default) mounts a fake project for real and keeps it busy (`TestSoak` in `cmd/ucfs`):
300 photos of 20–320 KB, every tenth 1–7 MiB, with 10 ms of CDN latency; all views; sync every second, sweep and group
sync every 30 s, `--meta-ttl 10s`, a 128 MiB cache. Other clients add a file and remove one every 3 s, change metadata
every 4 s and add a group a minute (keeping 10). Through the mount: an upload every 2 s (10–210 KB, the oldest of 40
removed), three readers reading random files of `files/` in full every 200 ms, walks of `tree/`, `tags/`, `groups/`
and `by-date/` every 10 s, and a variant read every 15 s. Every 30 s it samples the daemon's goroutines, descriptors
and heap (from `ucfs status --json`, which now reports them), its RSS (`ps`), the cache and the index into a CSV, and at
the end writes a heap profile. The daemon runs in the test process, with the fake; so the gauges include the fake's
own goroutines, connections and memory. The CSVs are in [phase5-soak/](phase5-soak/).

What the curves say:

- **Goroutines and descriptors do not grow** on any run: 23–45 goroutines and 31–43 descriptors on macOS, 36–58
  goroutines (spikes to about 130 while many FUSE requests were in flight) and 32–39 descriptors on Linux, 18 and
  21–25 live.
- **The cache stays at its limit** (128 MiB) once full; the live one holds the uploads it was seeded with.
- **The index grows with churn**, as designed: it keeps a row for every removed file, and about 9,000 files came and
  went in 3 hours, so the file grew from 5 to 9.5 MB while the present files stayed near 345. Live, it levelled at
  4.1 MB, the write-ahead log reaching SQLite's checkpoint size. Pruning old removed rows is deferred.
- **The heap does not grow on macOS**: 20–32 MiB at the half-hour marks, 26 MB in the profile at the end (transient
  response buffers, the node id table at 2.6 MB, which is bounded, and the fake's state). **RSS rose from 86 to
  108 MiB** over the 3 hours, which the Go heap does not explain; candidates are SQLite's own allocations (modernc's
  libc allocates outside the Go heap) and pages the runtime keeps after peaks (the heap peaked at 56 MiB). A 24-hour
  run will show whether it levels off.
- **The heap grew on Linux**, from 46 to 80 MiB, RSS from 124 to 184 MiB. The profile at the end: 14 MB of go-fuse
  request buffers, 14 MB of response buffers in flight, and about 15 MB of go-fuse's inode tree (`node.child`,
  `DisplayName`, the inode table): the kernel keeps a dentry for every file the readers listed, thousands of them
  removed since, and go-fuse keeps each node until the kernel forgets it, under memory pressure or when an access
  revalidates it (entry TTL 1 hour). That is the kernel's cache, not a leak, but it grows with churn; dropping the
  VM's caches 10 minutes into a 15-minute run took the sampled heap from 48 to 34 MiB, within the gauge's swing, so this
  is not proven. Telling the kernel about removed files (go-fuse `NotifyDelete` on the sweep) would let the nodes go;
  deferred.

## Found while measuring

- **macOS sent no uid over NFS**: go-nfs offered only `AUTH_NULL` at MOUNT, so ACCESS could not tell users apart and
  every user's ACCESS was granted (*Security*).
- **The control client leaked a connection per request**: each `ctl` call built a transport that kept its connection
  alive in a pool nothing reused, and the daemon held a goroutine for it. A CLI process exits and closes it, but the
  soak's sampler, a long-running caller, showed goroutines and descriptors growing with the number of samples (+18
  goroutines and +12 descriptors per six samples). The client now closes each connection; the first soak runs were
  stopped and started again on the fix.
- **`os.ReadDir("/dev/fd")` stops early on macOS** (`fstatat` of some entries fails), counting 3 descriptors; the count
  uses the names alone.
- **A prefetch could adopt a changed ETag silently**, and a stale stream from an earlier reader could fail a new one
  (*Read integrity*).
- **FUSE on Linux 7.x turns read errors into EIO** in the buffered path (*Traffic budget*), ENOENT and EINTR included.
- **Interrupted FUSE requests became EIO.** go-fuse cancels a request's context when a signal interrupts the process
  waiting on it, and the Go runtime signals its threads for preemption all the time, so the soak's Go readers got EIO
  for index queries the cancellation aborted: about 1,500 errors in 3 hours, with 76,000 `context canceled` lines in
  the log. Any Go program reading through a FUSE mount would hit it. A cancelled index query is now `EINTR`, which the
  caller retries, and reads no longer depend on the caller's context.
- **Duplicate refreshes.** A reader that found a file's info stale just before another reader's refresh ended
  started a second one; `TestLazyRefresh` failed 2 times in 40 under `-race` on Linux, the first time the suite ran
  with cgo there. The shared refresh, md5 `HEAD` and group read now check again inside the shared call.
- **An empty project's index has no cursor**, which the first version of the "index exists" check took for an unsynced
  index.
- **Two flaky NFS tests**: the RPC test client binds a random local port that may be in use, and keeps directory
  entries in a map, so their order varies; the tests retry the dial and sort.
- **CI could not run**: GitHub refused the jobs for the account's billing (*Benchmarks and CI*).
